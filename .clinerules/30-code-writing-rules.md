# Code Writing Rules

## Общие принципы
- Вносить только целевые изменения в рамках задачи.
- Сохранять существующий стиль и архитектурные границы проекта.
- Не смешивать функциональные изменения и массовый рефакторинг без явной необходимости.

## Для backend (Java)
- Соблюдать слойность: `controller -> service -> repository -> model`.
- Использовать DTO/mapper вместо прямой отдачи entity наружу.
- Не ломать обратную совместимость контрактов без явного требования в PRD.
- Использовать принипы SOLID в своей реализации.
- Использовать принципы DRY и YAGNI в своей реализации.
- Не усложнять код излишней оптимизацией.
- По завершению задачи, форматировать измененные файлы согласно ctrl+alt+l в IDEA и очищать неиспользуемые импорты.
- На реализуемый функционал писать интеграционные тесты или добавлять реализованную логику в существующие.

## Качество изменений
- Перед изменениями оценивать влияние на смежные модули и функционал.
- После изменений проверять компиляцию и тесты релевантного модуля.
- Документировать важные архитектурные решения в `memory-bank/06-system-development-progress.md`.

## Избегай чрезмерной проработки (over-engineering). 
Вноси только те изменения, которые непосредственно запрашиваются или явно необходимы. Делай решения простыми и целенаправленными:
- Область применения: Не добавляй функции, не рефактори код и не делай "улучшений" сверх того, что было предложено. Исправление ошибки не требует очистки окружающего кода. Простая функция не требует дополнительной настройки.
- Документация: Не добавляй строки документации, комментарии или аннотации типа к коду, который ты не менял. Добавляй комментарии только в тех случаях, когда логика не очевидна.
- Обработка ошибок: не добавляй обработку ошибок, резервные варианты или проверку для сценариев, которые не могут произойти. Доверяй внутреннему коду и гарантиям платформы
- Абстракции: Не создавай helper-классы, утилиты или абстракции для одноразовых операций. Не разрабатывай с учетом гипотетических будущих требований. Необходимый уровень сложности - это минимум, необходимый для текущей задачи.

## Тестирование
Пиши высококачественное решение общего назначения, используя доступные стандартные инструменты. Не создавай вспомогательные сценарии или обходные пути для более эффективного выполнения задачи. Реализуй решение, которое корректно работает со всеми допустимыми входными данными, а не только с тестовыми примерами. Не вводи жесткие значения и не создавай решения, которые работают только для определенных входных данных теста. Вместо этого реализуй реальную логику, которая решает проблему в целом.

Сосредоточься на понимании требований к задаче и реализации правильного алгоритма. Тесты предназначены для проверки правильности, а не для определения решения. Обеспечь принципиальную реализацию, соответствующую лучшим практикам и принципам разработки программного обеспечения.

Если задача является неразумной или невыполнимой, или если какие-либо тесты неверны, пожалуйста, сообщи мне об этом, а не пытайся обойти их. Решение должно быть надежным, поддерживаемым и расширяемым.

## Работа с кодом
Никогда не рассуждай о коде, который ты не открывал. Если пользователь ссылается на определенный файл, ты должен прочитать его, прежде чем отвечать. Обязательно изучи соответствующие файлы, прежде чем отвечать на вопросы о кодовой базе. Никогда не делай никаких заявлений о коде до начала исследования, если только ты не уверен в правильном ответе - давай обоснованные ответы, не допускающие галлюцинаций.

## Вопросы по коду
Если у тебя возникают какие-либо вопросы по выполнению задачи, формулировке, несоответствиям в требованиях и задаче - сразу задавай их пользователю и не начинай выполнение задачи без полного понимания требований и всех ограничений.
