## 2) SMTP-интеграция и fallback-поведение

## 2.1 Что реализовано
1. Есть абстракция `EmailService` с методом отправки ссылки установки пароля.
2. Есть 2 реализации:
   - `YandexSmtpEmailService` (`@ConditionalOnBean(JavaMailSender.class)`) — реальная отправка через SMTP;
   - `NoopEmailService` (`@ConditionalOnMissingBean(JavaMailSender.class)`) — fallback без отправки (только warning log).
3. Контур вызовов:
   - создание пользователя без пароля (`UserService.createUser`) → `sendPasswordLink`;
   - восстановление пароля (`AuthService.recoverPassword`) → `userService.sendPasswordLink`.
4. Конфигурация:
   - `app.mail.from`, `app.mail.invite-base-url`;
   - профиль `yandex-mail` в `application.yml` задаёт `spring.mail.*`.

## 2.2 Обнаруженные особенности/риски
1. **Нет ретраев/очереди/outbox** для email-отправки.
2. При активном `JavaMailSender` и ошибке `mailSender.send(...)` исключение пробрасывается вверх.
   - В `createUser` это происходит в рамках `@Transactional`: риск rollback операции создания пользователя при временной недоступности SMTP.
3. Fallback `NoopEmailService` сохраняет работоспособность API, но:
   - письмо фактически не отправляется;
   - лог содержит полный invite-link с токеном (чувствительные данные в логах).
4. Один и тот же email-шаблон используется и для onboarding, и для recovery (текст «Для установки пароля...»), что неявно для пользователя.

Вывод по SMTP: **partial** относительно `FR-002/FR-019` и `NFR-REL-04`.

## 3) YouTube и файловые пути в уроках

## 3.1 Что реализовано
1. Теория поддерживает форматы через `TheoryContentType`: `HTML_TEXT`, `VIDEO_URL`, `PDF_FILE`.
2. `TheoryLesson` хранит контент в строковом поле `content`; `lessonType` синхронизируется с `contentType`.
3. Студент получает `theoryContentType` + `theoryContent` через `GET /api/v1/student/lessons/{lessonId}`.

## 3.2 Обнаруженные ограничения/риски
1. Для `VIDEO_URL` и `PDF_FILE` нет валидации:
   - корректности URL,
   - доступности YouTube-ссылки,
   - существования/доступности файла.
2. Нет backend-механизма деградации для битых/недоступных ссылок (проверка, fallback-статус, метрики отказов).
3. Для PDF в теории используется строковый путь/ссылка, но нет специализированного upload/read API для учебных PDF внутри `monolith-mvp`.
4. Поля `coverFilePath`/`theoryContent` не проверяются на соответствие локальному хранилищу.

Вывод по контент-интеграциям: **partial** относительно `FR-007`, `AC-007`, `NFR-SCL-03`.

## 4) Файловое хранение

1. Фактическая файловая интеграция есть для аватаров (`app.storage.user-avatar-dir`, запись на локальный диск).
2. Для учебных PDF/материалов курса в монолите нет выделенного сервиса загрузки и валидации файлов — хранится «как есть» строкой в модели урока.
3. Это соответствует упрощённой MVP-модели, но создаёт разрыв между PRD-ожиданием «поддержка PDF-файла» и фактическим backend-контролем целостности пути.

Вывод: **partial** относительно ограничений PRD-04 и требований к эксплуатационной предсказуемости.

## 5) Деградационные сценарии (отказ внешних зависимостей)

| Сценарий | Текущее поведение | Оценка |
|---|---|---|
| SMTP не сконфигурирован (нет `JavaMailSender`) | Срабатывает `NoopEmailService`, API не падает, письмо не отправляется | partial |
| SMTP сконфигурирован, но временно недоступен | Исключение из `mailSender.send`, возможный срыв user-creation/recover flow | gap |
| YouTube-ссылка недоступна/заблокирована | Backend возвращает ссылку без проверки, фактический отказ проявляется только на клиенте | gap |
| PDF-путь невалиден/файл отсутствует | Backend возвращает путь без проверки, ошибка проявляется вне backend-контроля | gap |

Ключевой вывод: `NFR-REL-04` реализован **частично** — базовый учебный контур обычно живёт, но email-контур не имеет «контролируемого повтора» и может влиять на бизнес-операции при SMTP-сбоях.

## 7) Приоритизированные gap-и и рекомендации

1. **INT-GAP-007-01 (High): нет устойчивого email-delivery механизма**
   - Рекомендация: outbox + retry/backoff + dead-letter/event log; отделить факт создания пользователя от синхронной отправки письма.

2. **INT-GAP-007-02 (High): риск rollback user-операций при отказе SMTP**
   - Рекомендация: делать отправку асинхронно после фиксации транзакции либо переводить ошибки доставки в контролируемый статус «pending-notification».

3. **INT-GAP-007-03 (Medium): отсутствие валидации YouTube/PDF ссылок и file-path**
   - Рекомендация: добавить базовую валидацию формата и опциональную preflight-проверку доступности; централизовать ошибки контента.

4. **INT-GAP-007-04 (Medium): отсутствие полноценного backend-контура файлов учебных материалов**
   - Рекомендация: ввести upload/read API для учебных PDF и единый storage abstraction (локально в MVP).

5. **INT-GAP-007-05 (Critical): секреты SMTP/JWT/DB в `application.yml`**
   - Рекомендация: вынести в env/secret storage и ротировать скомпрометированные значения.

6. **INT-GAP-007-06 (Medium): логирование invite-link с токеном в `NoopEmailService`**
   - Рекомендация: маскировать/не логировать токен целиком.
