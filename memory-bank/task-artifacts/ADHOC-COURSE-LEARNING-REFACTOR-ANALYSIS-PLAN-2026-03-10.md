## 2) Подтверждённые требования (зафиксировано по комментариям заказчика)

## 2.1 Course: решения по полям

### Удалить в рефакторинге
- `deadlineAt`
- `allowContinueAfterFail`
- `keepAccessAfterDeadline`

### Оставить в текущей реализации БЕЗ добавления логики (пока как настраиваемые)
- `blockAfterDeadline`
- `includeInOverallStats`
- `passingThresholdPercent` (уровень курса)

## 2.2 Lesson-иерархия

- Единственный источник истины типа урока: **`lessonType`**.
- В `TheoryLesson` поле `contentType` — убрать.
- `TheoryLesson.syncLessonType()` — убрать (подтверждено).
- `PracticeLesson.syncLessonType()` — провести отдельный анализ необходимости; если не нужен, убрать.

## 2.3 PracticeQuestion

- `questionType` сделать **not-null** на уровне модели/БД.
- `options` и `correctAnswers` допускаются как nullable по текущей концепции (тестовые vs open-вопросы).
- Разрешено перейти на явную нормализацию `null -> empty list`, **если это заметно упростит код и сопровождение**.

## 2.4 LessonSubmission / статусы / JSON

- Вариант с terminal-флагом внутри `SubmissionStatus` (и вычисляемым `completed`) — допустим к рассмотрению, но только если не усложняет поддержку и контракты.
- Если решение не даёт явной пользы, оставить текущую модель `status + completed`.
- `reviewedByAdminId` / `reviewedAt` — оставить.
- Если `QuestionProgressJsonConverter` действительно не нужен для текущего маппинга поля, его можно удалить.

## 2.5 Сервисы и репозитории

- Архитектурную декомпозицию `CourseService`, `LearningService`, `StatisticsService`, а также зону `ProgramService` — делать только после отдельного анализа субагентами.
- Удалить неиспользуемые методы репозиториев.
- Отдельно проанализировать, каких агрегирующих запросов не хватает для снижения roundtrip к БД.

## 2.6 Мапперы / DTO

- По возможности убрать ручную DTO-обёртку в `CourseService` и перенести преобразования в мапперы.
- Работу с DTO на уровне сервисов минимизировать в пользу mapper-слоя.
- Можно ломать DTO-контракты для дополнительной/вспомогательной функциональности.
- Нельзя ломать ключевые контрактные части API.

## 2.7 Приоритет выполнения

- Приоритет №1: архитектурная декомпозиция сервисов.
- Но при декомпозиции обязательно контролировать производительность; если дробление ведёт к избыточной атомизации и росту DB-операций, перегруппировать границы сервисов более прагматично.

## Фаза B — Архитектурный анализ сервисов через субагентов (обязательно)

### B1. CourseService (субагент backend-architect)
Ожидаемое:
- целевые границы сервисов;
- что переносить/что оставить;
- список дублирующих/утилитарных методов для централизации;
- оценка влияния на транзакции и БД-вызовы.

### B2. LearningService (субагент backend-architect)
Ожидаемое:
- разрез по access policy / submit / review / scoring / enrollment lifecycle;
- точки дублирования и рекомендованные policy/utility-компоненты;
- риски race-condition и варианты упрощения.

### B3. StatisticsService + Repository layer (субагент backend-architect)
Ожидаемое:
- перечень недостающих агрегирующих запросов;
- предложения по снижению N+1 и массовых roundtrip;
- вариант разделения статистики и CSV-export логики.

### B4. ProgramService (субагент backend-architect)
Ожидаемое:
- целесообразная глубина включения ProgramService в первую волну рефакторинга;
- безопасные границы интеграции с course/learning flow.

Примечание: запуск субагентов должен выполняться по правилам `.clinerules/50-subagents-guidelines.en.md`.
