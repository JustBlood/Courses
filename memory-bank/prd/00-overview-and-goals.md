# PRD-00: Обзор и цели

## 1. Обзор продукта

### 1.1. Название и тип продукта
- **Название (рабочее):** Система корпоративного обучения.
- **Тип:** Внутренняя web-платформа для обучения сотрудников компании.

### 1.2. Проблема, которую решает продукт
Компания использует внешнее платное решение (Unicraft), что ограничивает гибкость настройки процессов обучения и увеличивает операционные затраты. Нужна собственная платформа с контролируемым roadmap, которая покрывает базовые процессы обучения и может поэтапно расширяться.

### 1.3. Продуктовое видение
Создать упрощённую, но масштабируемую LMS-платформу (Learning Management System), в которой:
- администратор управляет пользователями, курсами, группами, программами обучения и отчётностью;
- сотрудник (студент) проходит назначенное обучение и видит личный прогресс;
- практические задания проверяются автоматически (тесты) и вручную (развёрнутые ответы).

## 2. Цели и ожидаемый результат

### 2.1. Бизнес-цели
1. Уйти от зависимости от внешней платной платформы.
2. Сократить стоимость владения системой обучения на горизонте эксплуатации.
3. Повысить управляемость обучения (назначения, проверки, контроль завершений, отчётность).

### 2.2. Продуктовые цели
1. Запустить **MVP за 2 недели** с покрытием ключевых сценариев обучения.
2. За следующие **2 недели** добавить расширенный функционал (разделы, программы, группы, фильтры, расширенные параметры практики, восстановление пароля).
3. Сохранить архитектурный задел для дальнейших доработок без полной переработки системы.

### 2.3. Целевая аудитория
- Основная: сотрудники компании (студенты), которым нужно осваивать новые знания и навыки.
- Вторичная: администраторы обучения (управление контентом, пользователями, проверкой и статистикой).

## 3. Границы и состав релиза

### 3.1. Этап 1 — MVP (2 недели)
В MVP входят:
1. Управление пользователями (создание/редактирование, назначение ролей).
2. Онбординг пользователя через email-ссылку и установку пароля.
3. Управление курсами и уроками (теория + практика).
4. Зачисление/отчисление студентов на курсы.
5. Назначение проверяющих администраторов на курсы.
6. Прохождение курсов с автооценкой тестов и ручной проверкой развёрнутых ответов.
7. Личная статистика по курсам.
8. Статистика по курсу.
9. Сводный отчёт по завершениям.

### 3.2. Этап 2 — Расширение после демонстрации MVP (2 недели)
В post-MVP входят:
1. Разделы каталога курсов.
2. Программы обучения (последовательности курсов, дедлайн, условия доступа к следующему курсу).
3. Группы пользователей и массовые назначения через группы.
4. Поиск и фильтрация (курсы, пользователи, группы, статистика).
5. Расширенные параметры практических заданий:
   - порог прохождения;
   - ограничение попыток;
   - ограничение времени;
   - случайная выборка вопросов;
   - стоп-урок.
6. Восстановление пароля по email-коду.

### 3.3. Что не входит в текущие границы (Out of Scope)
- Мобильные приложения (iOS/Android).
- Интеграции с внешними HR/ERP-системами (в текущем ТЗ не зафиксированы).
- Продвинутая аналитика BI-уровня (дашборды вне описанных отчётов).
- Мультиязычность интерфейса.

## 4. Роли и режим работы ролей

### 4.1. Роли
- **Студент**
- **Администратор**

### 4.2. Важное правило ролевой модели
Роль администратора включает в себя возможности студента, однако в интерфейсе в каждый момент времени активна только одна роль (режим переключения контекста работы).

## 5. Ограничения и исходные условия

### 5.1. Инфраструктурные вводные заказчика
- Сервер: VPS или VM.
- ОС: Linux.
- Хранение материалов: локальное дисковое пространство сервера.
- Доступ: корпоративный домен.

### 5.2. Технологическая рамка backend
- **Текущая реализация backend (по коду `monolith-mvp`):**
  - Java 21, Spring Boot 3.2.x;
  - Spring Web, Spring Security, Spring Data JPA, Bean Validation;
  - JWT-аутентификация (`io.jsonwebtoken:jjwt`);
  - миграции БД через Flyway;
  - OpenAPI/Swagger через `springdoc-openapi`;
  - email-уведомления через `spring-boot-starter-mail`;
  - DTO/mapper-подход с MapStruct;
  - Lombok;
  - Apache Commons CSV (импорт/экспорт пользователей);
  - БД: H2 (локально) и PostgreSQL (runtime profile).
- **Инфраструктурный контекст (по репозиторию):**
  - контейнеризация и окружения через Docker Compose;
  - в проекте также есть контур микросервисной архитектуры (gateway/service discovery/очереди/объектное хранилище), что может использоваться как направление дальнейшего масштабирования.
- **Возможные технологии следующего этапа (по текущему контексту проекта):**
  - вынос частей функционала из монолита в сервисы,
  - Redis для кэширования/служебных сценариев,
  - Kafka для событийных интеграций,
  - MinIO/S3-совместимое хранилище для учебных материалов,
  - отдельный media-service для файлового домена.

## 6. Метрики успеха первой очереди
Минимальные метрики успешного запуска:
1. Администратор может полностью провести цикл: создать пользователя → назначить курс → получить факт прохождения в отчёте.
2. Студент может пройти назначенный курс до завершения, включая практику с ручной проверкой.
3. Отчёты отображают данные по завершениям и прогрессу без ручной выгрузки из БД.

### 6.1. Минимально обязательный end-to-end флоу (расширенный)
**Администратор должен иметь возможность:**
1. Войти в аккаунт.
2. Создать пользователя.
3. Создать курс.
4. Создать теоретический урок.
5. Создать практический урок.
6. Создать вопросы для практического урока.
7. Записать студента на курс.
8. Назначить себя проверяющим на курс.
9. После получения ответа студента на открытый вопрос:
   - отправить ответ на уточнение (повторную проверку),
   - затем принять ответ как выполненный.

**Студент должен иметь возможность:**
1. Установить пароль по токену и ссылке из email.
2. Войти в аккаунт.
3. Сменить пароль.
4. Восстановить пароль.
5. Просмотреть свои курсы.
6. Начать проходить курс.
7. Пройти тестовое практическое задание.
8. Отправить ответ на открытый вопрос.
9. Прочитать теоретический урок.
10. Получить свой профиль.

## 7. Зависимости и риски верхнего уровня

### 7.1. Зависимости
- Корректная доставка email (установка пароля, восстановление пароля).
- Доступность YouTube-ссылок для видео-уроков.
- Дисковая ёмкость для материалов курсов.

### 7.2. Основные риски
- Риск сдвига сроков при расширении предметной области post-MVP.
- Риск неявных правил проверки практики (особенно частично правильных ответов).
- Риск несоответствия между ТЗ и уже реализованным кодом без отдельного gap-анализа.

## 8. Источники требований
- Основной источник: пользовательское ТЗ «Система корпоративного обучения».
- Дополнительные источники: уточнения заказчика/разработчика в чате и последующих итерациях.
