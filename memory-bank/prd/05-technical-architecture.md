# PRD-05: Техническая архитектура

## 1. Назначение раздела
Фиксация целевой технической архитектуры платформы корпоративного обучения с учётом текущей реализации `monolith-mvp` и roadmap 2+2 недели.

---

## 2. Контекст и границы системы

### 2.1. Системный контекст
Платформа обеспечивает:
1. управление пользователями и ролями;
2. управление курсами и уроками;
3. назначение обучения (пользователи/группы/программы);
4. прохождение и проверку практики;
5. статистику и отчётность;
6. аутентификацию, смену/восстановление пароля.

### 2.2. Границы текущего контура
В границах текущей архитектуры:
- backend: `monolith-mvp` (Java/Spring Boot);
- БД: PostgreSQL (runtime), H2 (локально);
- файловое хранилище: локальный диск сервера;
- email: SMTP-интеграция;
- внешнее видео: YouTube links.

Вне текущих границ (как обязательство текущего релиза):
- отдельные мобильные приложения;
- внешние HR/ERP/LDAP/SSO интеграции;
- выделенный микросервисный production-контур.

---

## 3. Логическая архитектура (уровень модулей)

### 3.1. Модуль Identity & Access
Ответственность:
- login/logout;
- установка пароля по токену;
- смена и восстановление пароля;
- проверка ролей и прав доступа (RBAC).

### 3.2. Модуль User Management
Ответственность:
- CRUD пользователей;
- назначение ролей;
- профиль пользователя;
- импорт/экспорт пользователей (CSV).

### 3.3. Модуль Course & Lesson Management
Ответственность:
- CRUD курсов;
- управление уроками (`THEORY`, `PRACTICE`);
- управление вопросами практики;
- настройки прохождения курса/урока.

### 3.4. Модуль Enrollment & Reviewer Assignment
Ответственность:
- зачисление/отчисление студентов;
- назначение проверяющих администраторов;
- контроль доступов к прохождению.

### 3.5. Модуль Learning Flow
Ответственность:
- прохождение теории;
- автопроверка тестовой практики;
- workflow открытых ответов (ожидает проверки / на доработку / принято);
- начисление баллов и статусов выполнения.

### 3.6. Модуль Groups & Programs (post-MVP)
Ответственность:
- группы пользователей и массовые назначения;
- программы обучения (последовательность курсов, условия доступа, дедлайны).

### 3.7. Модуль Statistics & Reporting
Ответственность:
- личная статистика;
- статистика по курсу;
- сводные отчёты по завершениям.

---

## 4. Архитектурные слои backend

Принятая слойность:
`controller -> service -> repository -> model`.

Технические принципы:
1. API-контракты через DTO, без прямой отдачи entity наружу.
2. Бизнес-логика — в service-слое.
3. Доступ к данным — через repository.
4. Валидация входа — на уровне DTO + централизованный exception handling.

---

## 5. Концептуальная модель данных (укрупнённо)

Ключевые сущности:
1. `AppUser` — пользователь, роль, профильные и служебные поля.
2. `Course` — курс, параметры прохождения, метаданные.
3. `Lesson` (`TheoryLesson`/`PracticeLesson`) — единица обучения.
4. `PracticeQuestion` — вопрос практического урока.
5. `Enrollment` — назначение пользователя на курс.
6. `CourseReviewer` — назначение проверяющего на курс.
7. `LessonSubmission` — попытка/ответ пользователя и статус проверки.
8. `LearningGroup`, `GroupMembership` — группы и состав.
9. `LearningProgram`, `ProgramCourse`, `ProgramEnrollment` — программы и назначения.
10. `PasswordSetupToken` — токены активации/восстановления пароля.

---

## 6. Интеграции

### 6.1. SMTP
Используется для:
- отправки ссылок установки пароля;
- восстановления пароля.

### 6.2. YouTube
Используется как внешний источник видеоуроков по URL.

### 6.3. Корпоративный домен/SSL
Используется как внешний entrypoint к системе на прод-контуре.

---

## 7. Deployment-архитектура (VPS Linux)

### 7.1. Базовый вариант (MVP)
1. Один backend-инстанс `monolith-mvp`.
2. Одна БД PostgreSQL.
3. Локальное файловое хранилище на сервере.
4. Reverse proxy (Nginx/аналог) + TLS.

### 7.2. Усиленный вариант (post-MVP)
1. Выделение окружений dev/stage/prod.
2. Регламент backup/restore (БД + файлы).
3. Базовый мониторинг и alerting по SLO.

---

## 8. Безопасность архитектуры

1. JWT для API-сессий.
2. RBAC по ролям `ADMIN/STUDENT` и контексту назначений.
3. Хеширование паролей.
4. Ограничение частоты запросов на auth-endpoints.
5. Не хранить секреты в коде/репозитории; использовать env/secret-store окружения.
6. TLS-шифрование трафика на эксплуатационном контуре.

---

## 9. Наблюдаемость и эксплуатация

1. Логи приложения с корреляционным ID.
2. Метрики: latency, error rate, auth errors, email delivery.
3. Технические алерты:
   - рост 5xx;
   - недоступность БД;
   - сбои SMTP;
   - превышение времени отклика выше SLO.

---

## 10. Масштабирование и эволюция архитектуры

### 10.1. Краткосрочно
Вертикальное масштабирование (CPU/RAM/IOPS) монолита и БД.

### 10.2. Среднесрочно
Постепенный вынос модулей с высокой нагрузкой/изменчивостью (например, media/reporting) в отдельные сервисы без изменения бизнес-контрактов PRD.

### 10.3. Долгосрочно
Опциональный переход к:
- объектному хранилищу для файлов;
- кэшу Redis;
- событийной интеграции через очередь сообщений.

---

## 11. Архитектурные решения и trade-offs

1. Монолит как целевой runtime первой очереди выбран для соблюдения сроков и бюджета.
2. Локальное файловое хранение выбрано как более простое и дешёвое для запуска.
3. YouTube-ссылки выбраны вместо собственного видеохранилища/транскодинга.
4. Технический долг контролируется через жёсткое ограничение scope текущими FR.
