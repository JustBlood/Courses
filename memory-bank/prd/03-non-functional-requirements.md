# PRD-03: Нефункциональные требования

## 1. Назначение и принцип фиксации NFR
Этот раздел фиксирует измеримые нефункциональные требования для платформы корпоративного обучения.

Принцип фиксации (согласован с заказчиком):
- **MVP:** минимально реализуемый и проверяемый уровень в текущем `monolith-mvp`.
- **Post-MVP:** целевой уровень качества после завершения второй очереди (2+2 недели).

---

## 2. Производительность

### NFR-PERF-01. Время ответа API (read)
- **MVP:** p95 ≤ 700 мс, p99 ≤ 1200 мс для типовых операций чтения (профиль, каталоги, карточка курса, статистика).
- **Post-MVP:** p95 ≤ 500 мс, p99 ≤ 900 мс.

### NFR-PERF-02. Время ответа API (write)
- **MVP:** p95 ≤ 1000 мс, p99 ≤ 1800 мс для create/update/assignment.
- **Post-MVP:** p95 ≤ 800 мс, p99 ≤ 1500 мс.

### NFR-PERF-03. Аутентификация
- **MVP:** login и операции смены/восстановления пароля p95 ≤ 500 мс.
- **Post-MVP:** p95 ≤ 400 мс.

### NFR-PERF-04. Отчёты
- **MVP:** экранный просмотр отчётов до 1000 строк формируется ≤ 5 сек.
- **Post-MVP:** экспорт/генерация отчёта до 10 000 строк ≤ 30 сек.

### NFR-PERF-05. Параллельная нагрузка
- **MVP:** не менее 100 одновременных активных пользователей без нарушения SLO.
- **Post-MVP:** не менее 500 одновременных активных пользователей без нарушения SLO.

---

## 3. Надёжность и доступность

### NFR-REL-01. Уровень доступности
- **MVP:** uptime backend не ниже 99.0% в месяц.
- **Post-MVP:** uptime backend не ниже 99.5% в месяц.

### NFR-REL-02. Ошибки сервера
- **MVP:** доля ответов 5xx < 1.0%.
- **Post-MVP:** доля ответов 5xx < 0.5%.

### NFR-REL-03. Критичные бизнес-операции
Для операций создания пользователя, назначения на курс, отправки ответа, проверки ответа — подтверждённая фиксация в БД не ниже 99.9%.

### NFR-REL-04. Деградация внешних зависимостей
При недоступности email-провайдера базовый учебный контур (вход по действующим данным, прохождение, проверка, статистика) остаётся доступным; операции отправки писем переходят в контролируемое состояние ошибки с возможностью повтора.

---

## 4. Безопасность

### NFR-SEC-01. Аутентификация и сессии
- JWT-based аутентификация.
- Истечение токена и проверка подписи обязательны.
- Пароли хранятся только в виде стойкого хеша.

### NFR-SEC-02. Авторизация и RBAC
- Доступ к API определяется ролью (`STUDENT`, `ADMIN`) и бизнес-правилами назначений.
- Админские операции недоступны для роли студента.

### NFR-SEC-03. Защита персональных данных
- Передача данных только по HTTPS (на контуре эксплуатации).
- Маскирование/минимизация чувствительных полей в логах.
- Исключение хранения паролей и токенов в открытом виде в БД/логах.

### NFR-SEC-04. Защита от злоупотреблений
- Ограничение частоты запросов на login / password reset.
- Блокировка/замедление при серии неуспешных попыток.

### NFR-SEC-05. Управление секретами
- Секреты (JWT key, SMTP credentials, DB credentials) не хранятся в репозитории в открытом виде.
- Для runtime используются переменные окружения/секрет-хранилище окружения.

---

## 5. Целостность данных и транзакционность

### NFR-DATA-01. Консистентность назначений
Операции назначения/отчисления, назначения проверяющих, добавления в группы выполняются атомарно в рамках транзакции.

### NFR-DATA-02. Миграции БД
Изменения схемы БД выполняются только через версионируемые миграции.

### NFR-DATA-03. Идемпотентность повторов
Повторные запросы из-за сетевых retry не должны приводить к дублированию критичных связей (enrollment, reviewer assignment).

---

## 6. Наблюдаемость и аудит

### NFR-OBS-01. Логи
- Централизованное логирование API-ошибок, ключевых бизнес-событий и интеграционных ошибок email.
- Корреляционный идентификатор запроса в логах обязателен.

### NFR-AUD-01. Аудит действий
- Должны фиксироваться: кто создал/обновил пользователя, кто назначил курс/проверяющего, кто проверил развёрнутый ответ.

---

## 7. Резервное копирование и восстановление

### NFR-BCK-01. Backup БД
- **MVP:** ежедневный backup, хранение не менее 7 дней.
- **Post-MVP:** ежедневный full + внутридневные инкрементальные (или WAL-based), хранение не менее 14 дней.

### NFR-BCK-02. Backup файлов
- Резервирование папок учебных материалов и аватаров не реже 1 раза в сутки.

### NFR-BCK-03. Цели восстановления
- **MVP:** RPO ≤ 24 часа, RTO ≤ 8 часов.
- **Post-MVP:** RPO ≤ 4 часа, RTO ≤ 2 часа.

---

## 8. Масштабируемость и эволюция

### NFR-SCL-01. Вертикальное масштабирование
Система должна поддерживать масштабирование за счёт увеличения ресурсов VPS без изменения бизнес-логики.

### NFR-SCL-02. Горизонтальная эволюция
Архитектурные границы должны допускать вынос функциональных блоков из монолита в отдельные сервисы на следующих этапах.

### NFR-SCL-03. Файловое хранилище
Локальное хранение файлов в MVP/Post-MVP, с возможностью миграции в объектное хранилище в будущем.

## 10. Критерии проверки NFR
1. Нагрузочный smoke-тест на целевые сценарии read/write/login.
2. Проверка журнала ошибок и метрик за тестовый период.
3. Проверка отказа email-канала (деградационный сценарий).
4. Тест восстановления из backup (БД + файлы) с фиксацией фактических RPO/RTO.
