# PRD-04: Ограничения и допущения

## 1. Назначение раздела
Фиксация технических, продуктовых и процессных ограничений, а также явных допущений, в рамках которых должен быть реализован продукт.

---

## 2. Технические ограничения

### 2.1. Инфраструктура заказчика (из ТЗ)
1. Развёртывание выполняется на выделенном VPS/VM.
2. Целевая ОС: Linux.
3. Файлы учебных материалов хранятся на локальном диске сервера.
4. Доступ к платформе осуществляется через корпоративный домен.

### 2.2. Технологическая рамка текущей реализации
1. Базовый backend-контур: `monolith-mvp` (Java/Spring Boot).
2. Аутентификация: email/password + JWT.
3. База данных: H2 для локального режима, PostgreSQL как целевой runtime-профиль.
4. Изменения схемы БД — только через Flyway-миграции.
5. Email-контур обязателен для установки и восстановления пароля.

### 2.3. Ограничения интеграций
1. Интеграции с внешними HR/ERP/LDAP/SSO в текущем PRD не являются обязательными.
2. Видео-контент на этапе MVP/post-MVP — через ссылки на YouTube, без собственного видеохостинга.
3. Для отправки email используется SMTP-провайдер, предоставляемый средой эксплуатации.

---

## 3. Продуктовые ограничения

1. Обязательные роли в MVP: `STUDENT`, `ADMIN`.
2. Администратор включает функционал студента, но в UI в момент времени активен один режим роли.
3. Scope MVP ограничен требованиями FR-001..FR-019.
4. Scope post-MVP ограничен требованиями FR-101..FR-114.
5. Мобильные приложения, BI-аналитика и внешние enterprise-интеграции — вне границ текущей итерации.

---

## 4. Процессные ограничения

1. Сроки разработки:
   - MVP: 2 недели;
   - post-MVP расширение: 2 недели.
2. Бюджет полного объёма работ (MVP + post-MVP): 50 000 ₽.
3. Изменения вне согласованных FR требуют отдельного согласования и пересмотра сроков/бюджета.

---

## 5. Допущения

### 5.1. Допущения по пользователям и нагрузке
1. На старте система используется как внутренний корпоративный продукт с умеренной одновременной нагрузкой.
2. Базовый уровень эксплуатационной нагрузки соответствует NFR для MVP (до 100 одновременно активных пользователей).

### 5.2. Допущения по данным
1. Учетная запись пользователя опирается на уникальный email.
2. В отчётах поле `login` может быть пустым/служебным в соответствии с согласованным форматом.
3. Первичным источником прав доступа является роль пользователя и явные назначения (курс/группа/программа).

### 5.3. Допущения по контенту
1. Материалы курсов (изображения, PDF, аватары) укладываются в доступный дисковый объём сервера.
2. Форматы контента соответствуют поддерживаемым типам теоретических и практических уроков из FR.

### 5.4. Допущения по эксплуатации
1. Заказчик обеспечивает базовую администрируемость сервера (резервное копирование, SSL, мониторинг уровня хоста).
2. SMTP и домен считаются доступными и корректно настроенными на контуре эксплуатации.

---

## 6. Ограничения и допущения по качеству

1. На MVP целевой уровень качества фиксируется как «минимально реализуемый в текущем монолите».
2. На post-MVP целевой уровень качества доводится до значений NFR (производительность, отказоустойчивость, наблюдаемость).
3. При конфликте сроков и функциональности приоритет отдаётся сохранению корректности ключевых бизнес-сценариев:
   - создание пользователя и установка пароля;
   - назначение на курс;
   - прохождение и проверка практики;
   - получение статистики и отчётов.

---

## 7. Зафиксированные trade-off решения

1. **Скорость поставки vs архитектурная сложность:**
   выбран монолитный runtime для MVP/post-MVP вместо обязательного микросервисного распила.
2. **Простота контента vs функциональная гибкость:**
   видео через YouTube-ссылки вместо собственного стриминга.
3. **Стоимость инфраструктуры vs масштабируемость:**
   локальное файловое хранение на старте с последующим опциональным переходом к объектному хранилищу.
4. **Бюджет vs расширение scope:**
   функции за пределами FR-001..FR-019 и FR-101..FR-114 не включаются в текущую оценку 50 000 ₽.

---

## 8. Критические зависимости

1. Доступность SMTP-канала для onboarding и восстановления пароля.
2. Корректная работа хранилища БД и файлового диска.
3. Наличие и работоспособность SSL/TLS на корпоративном домене.
4. Доступность YouTube для воспроизведения внешних видеоуроков.
