# PRD-02: Функциональные требования

## 1. Общие правила функционала

### 1.1. Роли и доступ
1. Система поддерживает роли: `STUDENT`, `ADMIN`.
2. `ADMIN` имеет доступ к функциям студента и функциям администрирования.
3. В интерфейсе одновременно активен один режим роли (student/admin mode).

### 1.2. Единицы контента и прогресса
1. Базовая единица обучения — **курс**.
2. Курс состоит из **уроков** двух типов: `THEORY`, `PRACTICE`.
3. Прогресс по курсу считается по урокам:
   - пройденность конкретного урока определяется результатом выполнения его заданий;
   - баллы урока считаются по выполненным заданиям/ответам;
   - пройденность курса определяется агрегированным результатом по урокам курса.
4. Отчётность формируется на уровне полученных баллов: сколько пользователь набрал из максимально возможного по курсу.

### 1.3. Балльная модель
1. Для уроков и/или вопросов задаются баллы.
2. Допускается дефолтная настройка баллов + переопределение на уровне конкретного урока.
3. Для тестов с множественным выбором должна поддерживаться частичная оценка (частично правильный ответ).
4. Дефолтные баллы:
   - `1` — за верный ответ,
   - `0` — за частично правильный,
   - `0` — за неверный/невыполненный.

## 2. MVP — обязательные функциональные требования

Ниже требования сгруппированы по модулям. Формат: **FR-XXX**.

### 2.1. Модуль пользователей и профиля

**FR-001. Создание пользователя администратором**
- Администратор должен иметь возможность создать пользователя с полями:
  - ФИО,
  - email,
  - роль (тип учётной записи),
  - enabled,
  - phone,
  - comment,
  - createdAt,
  - createdBy,
  - lastVisit,
  - deactivatedAt,
  - deactivatedBy,
  - avatarFilePath.
- При создании администратор может сразу:
  - добавить пользователя в существующие группы,
  - записать пользователя на выбранные курсы.

**FR-002. Активация аккаунта через email-ссылку**
- После создания пользователя система отправляет email с уникальной ссылкой.
- По ссылке пользователь задаёт пароль (по схеме, аналогичной восстановлению пароля).
- До установки пароля пользователь не считается полностью активированным.

**FR-003. Редактирование пользователей**
- Администратор должен иметь возможность редактировать данные любого пользователя.
- Пользователь должен иметь возможность просматривать и редактировать свой личный профиль (в пределах разрешённых полей).

**FR-004. Назначение/изменение ролей**
- Администратор должен иметь возможность назначать и изменять роль пользователя.
- Изменение роли должно мгновенно влиять на доступные функции.

### 2.2. Модуль курсов и уроков

**FR-005. Создание и редактирование курса**
- Администратор может создать/редактировать курс со свойствами:
  - название,
  - описание,
  - обложка (фото),
  - порог прохождения курса,
  - deadlineDays,
  - authorFullName,
  - lessonsFreeOrder,
  - allowContinueAfterFail,
  - createdByAdminId.

**FR-006. Структура уроков курса**
- Курс поддерживает уроки типа:
  1. `THEORY` (теоретические),
  2. `PRACTICE` (практические).

**FR-007. Теоретический урок**
- Теоретический урок поддерживает контент форматов:
  - текст,
  - видео по ссылке YouTube,
  - PDF-файл.

**FR-008. Практический урок: типы вопросов**
- Практический урок должен поддерживать вопросы:
  - один верный ответ,
  - несколько верных ответов,
  - сопоставление,
  - порядок (расстановка в нужной последовательности),
  - развёрнутый ответ.

**FR-009. Настройка баллов**
- Система должна поддерживать:
  - настройку баллов по умолчанию,
  - настройку баллов в конкретном уроке,
  - частичные баллы для множественного выбора.

### 2.3. Модуль зачислений и назначений

**FR-010. Зачисление/отчисление студентов на курс**
- В настройках курса отображаются два списка:
  - не зачисленные,
  - зачисленные.
- Администратор может перемещать выбранных пользователей между списками.

**FR-011. Назначение проверяющих администраторов**
- В настройках курса администратор выбирает проверяющих из пользователей с ролью `ADMIN`.
- Назначенным проверяющим доступна вкладка/раздел «Проверка».
- Раздел «Проверка» должен показывать:
  - назначенные курсы,
  - задания с развёрнутым ответом, ожидающие проверки.

### 2.4. Модуль прохождения обучения

**FR-012. Прохождение теории**
- Студент должен иметь доступ к теоретическим урокам назначенного курса.
- При фиксации прохождения теоретического урока система сразу начисляет баллы за этот урок.

**FR-013. Автопроверка тестовых заданий**
- После отправки тестовых ответов система автоматически:
  - проверяет результат,
  - фиксирует статус,
  - начисляет баллы.

**FR-014. Проверка развёрнутых ответов**
- После отправки развёрнутого ответа:
  - ответ получает статус ожидания проверки,
  - проверяющий администратор выставляет результат,
  - по факту проверки обновляется статус урока и начисляются баллы.

### 2.5. Модуль статистики и отчётности

**FR-015. Личная статистика студента**
- Для студента в профиле доступна статистика по пройденным/проходимым курсам.
- Для администратора аналогичная статистика доступна на странице пользователя.
- По каждой записи выводятся:
  - название курса,
  - полученные баллы,
  - эффективность,
  - процент выполнения.
- Формулы расчёта:
  - эффективность = `полученные баллы * 100 / максимальные баллы`;
  - процент выполнения = `количество выполненных уроков / общее количество уроков курса * 100`.

**FR-016. Статистика по конкретному курсу**
- На странице курса администратор видит статистику студентов:
  - ФИО,
  - полученные баллы,
  - эффективность,
  - процент выполнения.

**FR-017. Сводный отчёт по завершениям**
- Из каталога курсов по отдельному действию открывается сводный отчёт.
- **Сводный отчёт по конкретному курсу** должен содержать колонки:
  - Статус,
  - Программа,
  - ФИО,
  - Email,
  - Логин (всегда пустой),
  - cid (всегда пустой),
  - Деактивирован,
  - Компания,
  - Подразделение,
  - Должность,
  - Группы,
  - Баллов,
  - Эффективность,
  - Медалей (всегда пусто),
  - Пересдач,
  - Назначено,
  - Начало,
  - Завершение,
  - Дедлайн,
  - Затрачено времени,
  - Прогресс,
  - Уроков,
  - Продолжительность,
  - Номер сертификата (пустой),
  - Ссылка (пустой).
- **Общий сводный отчёт по всем курсам** должен содержать колонки:
  - Группы,
  - ФИО студента,
  - Email,
  - Логин (пусто),
  - CID (пусто),
  - Название курса,
  - CID (пусто),
  - Дата назначения,
  - Время,
  - Дата начала,
  - Время,
  - Дата завершения,
  - Время,
  - Баллов,
  - Эффективность,
  - Продолжительность,
  - Затрачено,
  - Номер сертификата (пусто),
  - Ссылка (пусто).

**FR-018. Смена пароля (MVP)**
- Авторизованный пользователь может сменить пароль, указав текущий и новый пароль.

**FR-019. Восстановление пароля (MVP)**
- Пользователь может инициировать восстановление пароля по email и задать новый пароль через ссылку/токен.

## 3. Post-MVP — функциональные требования расширения

### 3.1. Разделы курсов

**FR-101. Создание и редактирование разделов**
- Администратор может создавать раздел с полями:
  - название,
  - описание,
  - приоритет вывода.

**FR-102. Связь раздела и курсов**
- Администратор может создавать курс прямо со страницы раздела.
- В этом случае курс автоматически относится к выбранному разделу.

### 3.2. Программы обучения

Программа является сущностью, которая содержит упорядоченный список уже существующих на платформе курсов. 
Программа необходима для упрощения флоу студентов - для логически верной последовательности прохождения курсов и для получения целого набора готовых навыков для освоения. 
Т.к. программа содержит в себе упорядоченный список уже существующих курсов и может быть назначена на пользователя - требуется тщательно продумать решение, чтобы не было коллизий прохождения курсов и программ. Если курс уже был пройден не в рамках программы - в программе он будет уже выполненным для пользователя и при любом условии прохождения, следующий курс автоматически должен стать доступным. Если курс ещё не был пройден/просмотрен пользователем самостоятельно, то в программе у него стандартное поведение. Требуется также корректно обрабатывать случаи, когда студент начал курс не в рамках программы и ещё не завершил его и он одновременно появился в рамках программы. В таком случае, прогресс должен быть сохранён и студент должен продолжать выполнение в рамках программы с того же места, как в индивидуальном порядке и наоборот. При записи на программу, студент не записывается на все курсы сразу - они открываются по мере прохождения курсов, в зависимости от условий прохождения. При получении студентом программы, он получает краткую информацию о них, если курс пройден - свои баллы и статус прохождения. Если один из курсов в рамках программы завершен неудачно - то администратор, назначенный проверяющим на курс, может переназначить пользователю курс и он будет проходить его заново. Данный функционал по переназначению курса, должен присутствовать также и на обычных курсах, вне рамок программ обучения.

**FR-103. Создание и редактирование программ**
- Администратор может создать программу обучения, содержащую упорядоченный список курсов.

**FR-104. Правила прохождения программы**
- Для программы настраиваются:
  - дедлайн,
  - условие прохождения одного из трех видов:
    1) все курсы доступны в любой момент;
    2) следующий курс доступен после завершения.
    3) следующий курс доступен после просмотра предыдущего.

**FR-105. Назначение программ**
- Программа может быть назначена:
  - отдельному студенту,
  - группе студентов.

### 3.3. Группы пользователей

**FR-106. Создание и редактирование групп**
- При создании группы задаются:
  - название,
  - тип группы: `ОБЩАЯ`, `КОМПАНИЯ`, `ПОДРАЗДЕЛЕНИЕ`, `ДОЛЖНОСТЬ`.

**FR-107. Включение пользователя в группы**
- При создании/редактировании пользователя администратор может назначать его в существующие группы.

**FR-108. Массовые назначения через группы**
- Администратор может назначать курсы и программы группе.
- Назначение группе автоматически распространяется на всех её участников.

### 3.4. Поиск и фильтрация

**FR-109. Поиск/фильтры в ключевых каталогах**
- Система должна поддерживать поиск и фильтрацию на страницах:
  - каталога курсов,
  - пользователей,
  - групп.

### 3.5. Расширенные параметры практических заданий

**FR-110. Порог прохождения практики**
- Для практического урока настраивается порог прохождения по баллам/проценту результата (какое количество баллов необходимо набрать, чтобы урок считался выполненным).

**FR-111. Ограничение попыток**
- Для урока задаётся лимит попыток прохождения (`attemptLimit`).

**FR-112. Ограничение времени**
- Ограничения времени задаются на двух уровнях:
  - на курс — в днях (`deadlineDays`),
  - на урок — в минутах (`timeLimitMinutes`).

**FR-113. Случайная выборка вопросов**
- Поддерживаются оба режима:
  1) рандомизация порядка вопросов в каждой попытке (`shuffleOnEveryAttempt`),
  2) ограниченная выборка вопросов из банка (`randomQuestionCount`).

**FR-114. Stop-lesson правило**
- Если на уроке включён режим `stopLesson`, переход к следующему уроку блокируется до прохождения текущего.
- Ограничение действует совместно с параметром курса `lessonsFreeOrder`: даже при свободном порядке уроков stop-lesson остаётся блокирующим для перехода дальше.

### 3.6. Восстановление пароля

**FR-115. Email-восстановление пароля**
- Удалено из post-MVP; перенесено в MVP как `FR-019`.

## 4. Бизнес-правила (агрегировано)
1. Пользователь может проходить только те курсы/программы, к которым ему предоставлен доступ.
2. Проверка развёрнутых ответов выполняется только назначенными проверяющими администраторами.
3. Метрики эффективности и выполнения должны рассчитываться единообразно во всех отчётных представлениях.
4. Любые изменения назначений (курс/группа/программа) должны влиять на доступы без ручных технических операций.

## 5. Трассировка к разделу критериев приёмки
Каждое требование `FR-XXX` должно иметь проверяемый критерий в `PRD-05: Критерии приемки` (будет детализировано в следующих итерациях).
