# PRD-01: Пользовательские сценарии

## 1. Роли и контекст использования

### 1.1. Роль «Студент»
**Цель роли:** пройти назначенное обучение, набрать проходной результат, видеть прогресс.

**Ключевые задачи (Jobs-to-be-done):**
1. Войти в платформу и настроить профиль.
2. Найти назначенные курсы/программы.
3. Пройти теоретические и практические уроки.
4. Пройти курс до конца и получить итоговую оценку в баллах.
5. Сменить пароль в личном кабинете.
6. Восстановить пароль при утрате доступа.

### 1.2. Роль «Администратор»
**Цель роли:** управлять процессом обучения и контролировать результаты.

**Ключевые задачи (Jobs-to-be-done):**
1. Создавать, удалять (точечно и массово), изменять пользователей, курсы, уроки, вопросы, группы пользователей и программы обучения.
2. Назначать студентов на курсы точечно и назначать группы студентов на курсы массово.
3. Назначать администраторов-проверяющих на курсы (точечно и массово). Проверять развёрнутые ответы студентов, если администратор назначен проверяющим.
4. Иметь возможность импортировать и экспортировать пользователей, их прогресс по курсам в заданном формате.

### 1.3. Режимы ролей
Пользователь с правами администратора имеет все функции студента и может работать в режиме студента и в режиме администратора, но одновременно активен только один режим (переключение в UI).

## 2. Основные пользовательские сценарии MVP

### US-01. Первичный доступ сотрудника в систему
**Актор:** Администратор, затем Студент.

**Предусловия:**
- пользователь ещё не активировал аккаунт;
- администратор всегда имеет доступ к созданию пользователей.

**Основной поток:**
1. Администратор создаёт пользователя (ФИО, email, роль; логин не используется).
2. Администратор при необходимости сразу назначает группы/курсы.
3. Система отправляет email с уникальной ссылкой установки пароля.
4. Студент переходит по ссылке, задаёт пароль.
5. Студент входит в систему и заполняет профиль.

**Результат:** активный аккаунт сотрудника, готовый к обучению.

### US-02. Управление курсом и контентом
**Актор:** Администратор.

**Предусловия:** администратор по умолчанию имеет доступ к управлению курсами и контентом.

**Основной поток:**
1. Администратор создаёт курс (название, описание, обложка, порог прохождения).
2. Добавляет уроки:
   - теория (текст / YouTube-видео / PDF);
   - практика (тесты разных типов / развёрнутые ответы).
3. Настраивает баллы по умолчанию и (опционально) переопределяет баллы на уровне урока/вопроса.

**Результат:** опубликованный/готовый курс с измеримыми критериями прохождения.

### US-03. Зачисление студентов и назначение проверяющих
**Актор:** Администратор.

**Предусловия:** в системе есть пользователи и курс.

**Основной поток:**
1. Администратор открывает настройки курса.
2. Перемещает студентов между списками «не зачислены» и «зачислены».
3. Аналогично назначает проверяющих из администраторов.
4. У проверяющих появляется рабочая область «Проверка».

**Результат:** сформирован состав обучающихся и ответственных за ручную проверку.

### US-04. Прохождение курса студентом
**Актор:** Студент.

**Предусловия:** студент зачислен на курс.

**Основной поток:**
1. Студент открывает назначенный курс.
2. Изучает теорию и получает баллы за просмотр теоретических уроков.
3. Выполняет тестовые задания — система автоматически проверяет и начисляет баллы.
4. Выполняет задания с развёрнутым ответом — отправляет на проверку.
5. После проверки администратором система обновляет статус урока и итоговые баллы.

**Результат:** курс проходит по установленным правилам, прогресс фиксируется.

### US-05. Контроль результатов обучения
**Актор:** Студент и Администратор.

**Основной поток для студента:**
1. Открыть личную статистику.
2. Просмотреть по каждому курсу: баллы, эффективность, % выполнения.

**Основной поток для администратора:**
1. Открыть страницу пользователя и его статистику.
2. Открыть статистику по конкретному курсу.
3. Открыть сводный отчёт по завершениям.

**Результат:** обе роли получают прозрачную картину прогресса и завершений.

### US-11. Восстановление пароля (MVP)
Пользователь инициирует восстановление по email, получает ссылку/код подтверждения, задаёт новый пароль и восстанавливает доступ.

### US-12. Смена пароля (MVP)
Пользователь в авторизованной сессии подтверждает текущий пароль, задаёт новый и продолжает работу с обновлёнными данными доступа.

## 3. Основные пользовательские сценарии post-MVP

### US-06. Навигация по разделам каталога
Администратор создаёт разделы и управляет структурой выдачи курсов; дополнительно администратор может вручную задавать единый для всей платформы порядок отображения курсов в ленте, который видят пользователи.

### US-07. Обучение по программам
Администратор формирует программу из курсов, задаёт дедлайн и условие доступа к следующему курсу; назначает программу пользователю или группе; студент проходит программу последовательно.

### US-08. Массовое администрирование через группы
Администратор создаёт группы (общая/компания/подразделение/должность), добавляет участников и назначает группе курсы/программы. Для одного пользователя допускается не более одной группы каждого типа: «компания», «подразделение», «должность», и неограниченное количество групп типа «общая».

### US-09. Поиск на платформе
На платформе есть система поиска курсов, пользователей и групп по наименованию/ФИО как для администраторов, так и для пользователей — с отображением результатов в соответствии с правами доступа.

### US-10. Расширенный контроль прохождения практики
Администратор задаёт параметры прохождения с учётом действующей модели backend:
1. **Порог прохождения урока** — сколько баллов/какой порог нужно набрать, чтобы урок считался выполненным.
2. **Ограничение попыток** — максимальное количество попыток на прохождение урока.
3. **Ограничение по времени**:
   - на курс — в днях;
   - на урок — в минутах.
4. **Рандомизация вопросов** — вопросы практического урока показываются в случайном порядке в каждой попытке.
5. **Ограниченная выборка из банка** — в попытку попадает заданное количество вопросов из общего набора урока.
6. **Stop-lesson** — пока урок не пройден, переход к следующему уроку запрещён; правило работает совместно с параметром курса `lessonsFreeOrder` (если свободный доступ включён, stop-lesson всё равно блокирует переход дальше).

## 4. Альтернативные и исключительные потоки (высокий уровень)
1. Ссылка установки пароля истекла → пользователь запрашивает новую ссылку через администратора/механизм восстановления.
2. Пользователь не назначен на курс → курс не отображается пользователю вообще.
3. Проверяющий не назначен, а есть развёрнутые ответы → ответы остаются в статусе ожидания до назначения.
4. Непрохождение порога по курсу/уроку → отображается статус «не пройдено», доступ к следующему шагу определяется правилами курса/программы.

## 5. UX-принципы, вытекающие из сценариев
1. Минимальное число шагов для администратора в массовых операциях назначения.
2. Явное отображение статусов (назначен, в процессе, ожидает проверки, завершён, не пройден).
3. Разделение интерфейса по режимам роли для снижения когнитивной нагрузки.
4. Прозрачная обратная связь по начислению баллов и причинам непрохождения.
